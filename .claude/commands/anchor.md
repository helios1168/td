Run the project's numeric anchor and **verify it**, which is two steps, not one.

`code/mkfig_zip50.py` is the regression test for `territory.py` and `districting.py`: it prints
every number §5 / §6 / Contestability / breakpoints / opportunity balance need, and rewrites
`figures/nash_solution.png`, `figures/zip50_nash_milp.png`, `figures/nash_contestability.png`.
If nothing moved, **those PNGs must come back byte-identical**. That property is the test —
running the script without checking it proves nothing.

## Before

The figures directory must be clean, or the byte-identity check is meaningless:

!`git status --short figures/`

If anything under `figures/` is already dirty, **stop and tell me** — I need to know whether
that's an uncommitted intentional change before you overwrite it.

## Run

`.venv/bin/python3 code/mkfig_zip50.py`   (~2 min from the repo root)

## Verify

1. `git status --short figures/` — expect **empty**. Any listed PNG means a number moved.
2. If a PNG did change, do **not** assume it's noise. Report which one, and diff the script's
   printed numbers against what the paper and `CLAUDE.md` currently quote — specifically the
   Contestability top-5 (zips 22 and 28) and the §5/§6 headline values.

## Report

- The printed numbers, as a compact block — these are the actual regression output.
- Byte-identity verdict per PNG: identical / changed.
- `zip50_distributions.png` is **not** regenerated by this script and is not expected to move;
  don't flag its absence from the output as a problem.
- If a figure moved, state it as a **finding**, not a fix, and stop. Whether a moved anchor is a
  regression or a deliberate refresh is my call.
