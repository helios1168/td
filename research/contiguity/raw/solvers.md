# Open-source solver stacks for convex-MINLP + connectivity separator cuts (400-800 binaries)

Scope: verify, against fetched docs/GitHub source, what each open-source stack can do for a
convex MINLP (max log g_a + log g_b via outer approximation) that also needs lazily-added
connectivity separator cuts during branch-and-bound. Gurobi/CPLEX/Xpress/Hexaly excluded by
project constraint (open-source only).

All claims below are cited to a URL actually fetched via WebFetch/WebSearch this session
(2026-08-28). Anything not confirmed against a primary source is marked **UNVERIFIED**.

## Per-stack notes with URLs

### HiGHS / highspy
- Callback types enumerated in official docs: `kCallbackLogging`, `kCallbackSimplexInterrupt`, `kCallbackIpmInterrupt`, `kCallbackMipImprovingSolution`, `kCallbackMipSolution`, `kCallbackMipLogging`, `kCallbackMipInterrupt`, `kCallbackMipUserSolution`, `kCallbackMipGetCutPool`. Source: https://ergo-code.github.io/HiGHS/dev/callbacks/ (fetched directly). All are read-only status/telemetry callbacks except `kCallbackMipUserSolution` (push a candidate integer-feasible *solution* in) and `kCallbackMipGetCutPool` (pull cuts generated at the root — retrieval, not injection). **No cut/constraint injection API exists.** This directly explains why the project's current approach re-solves `scipy.optimize.milp` (HiGHS) from scratch each round instead of using a lazy-cut callback: **that capability does not exist in HiGHS today.**
- Maintainer confirmation that highspy's Python layer is intentionally minimal and callbacks for cut injection are not on the roadmap without contributed effort: https://github.com/ERGO-Code/HiGHS/discussions/1831 (fetched; maintainer quote: "we can't see us developing the modelling features of highspy much... It's just there to allow simple illustrative examples"; a contributor floated implementing Gurobi/COPT-style callbacks "with some effort" but nothing shipped as of this discussion).
- Parallel MIP: a genuine parallel branch-and-bound MIP solver landed around HiGHS **v1.15** (`parallel` option, `threads` option; default `threads=0` uses half the machine's cores). Source: WebSearch results on HiGHS release notes / docs (https://ergo-code.github.io/HiGHS/dev/parallel/, https://highs.dev/, https://github.com/ERGO-Code/HiGHS/issues/506) — not independently re-fetched line-by-line, so treat the exact version number as **medium-confidence, not directly quoted from a fetched page**.
- License: MIT (confirmed via highspy PyPI metadata search). Wheels: arm64 macOS wheel confirmed present at highspy 1.15.1 (`macosx_11_0_arm64.whl`).

### SCIP / PySCIPOpt
- Lazy constraints tutorial fetched directly: https://pyscipopt.readthedocs.io/en/latest/tutorials/lazycons.html. Mechanism: subclass `Conshdlr`, implement `conscheck()` (feasibility check) and `consenfolp()` (enforce on LP relaxation — find a violated inequality, add it live with `addCons()`), register via `model.includeConshdlr(conshdlr, ...)`, add constraint instances via `addPyCons()`. Setting `chckpriority = -10` restricts enforcement to integer-feasible solutions only (i.e., true "lazy constraint" semantics rather than every-LP-node cutting). This is SCIP's **native, documented, first-class mechanism** for exactly the connectivity-separator-cut use case in this project (check candidate assignment for disconnection, add the violated cut, resume B&B) — no restart of the MIP required.
- Warm start API fetched via search, cross-checked against Model API docs (https://pyscipopt.readthedocs.io/en/stable/api/model.html): `model.createSol()` → `model.setSolVal(sol, var, value)` → `model.trySol(sol)` (or `addSol()`). `trySol()` has had historical bugs in older versions (GitHub issues #114, #487) — worth a smoke test on the pinned PySCIPOpt version before relying on it.
- Wheels: per PySCIPOpt's own INSTALL.md (https://github.com/scipopt/PySCIPOpt/blob/master/INSTALL.md, matched via search), **"From version 5.0.0 SCIP is automatically shipped when using PyPI"** for macOS x86_64/ARM64, CPython 3.8–3.12 (newer PySCIPOpt releases extend this; a `pyscipopt-6.2.1-cp314-cp314-macosx_11_0_arm64.whl` was observed). This means `pip install pyscipopt` on the project's macOS arm64 venv should work with **no separate SCIP binary install** — a meaningfully lower-friction install path than Bonmin/Couenne/SHOT.
- License: **Apache 2.0 confirmed from SCIP 8.0.3 onward** (ZIB Academic License applied through 8.0.2). Source: search results referencing https://www.scipopt.org/doc-8.0.3/html/LICENSE.php and https://github.com/google/or-tools/issues/3619 ("Update SCIP to latest version (8.0.3+) for SCIP Apache 2.0 License").
- Convex MINLP: SCIP treats nonlinear constraints (including exp/log-type expressions once reformulated to SCIP's expression graph) via spatial branch-and-bound with convexity detection, giving a certified global optimum — this is a materially different (stronger) guarantee path than an externally-hand-rolled outer-approximation loop, because SCIP's own presolve/convexity detection plus the nonlinear handler line up with what this project's log-objective needs. Not independently re-verified against a fetched "SCIP nonlinear handler" doc page in this session — flagging as **medium confidence**, recommend a direct read of SCIP's `cons_nonlinear`/`nlhdlr` docs before committing.
- Parallelism: no in-process parallel B&B in vanilla SCIP/PySCIPOpt (threads confined to presolve / convexity checks / Ipopt linear algebra); genuine parallel search requires the separate ParaSCIP/FiberSCIP builds under the UG framework, which PySCIPOpt does not expose. Source: search results on ParaSCIP/FiberSCIP docs (https://optimization-online.org/2017/04/5944/, https://arxiv.org/pdf/2402.17702).

### CBC / python-mip
- Custom branch-and-cut docs fetched directly: https://python-mip.readthedocs.io/en/latest/custom.html. `ConstrsGenerator.generate_constrs(model, depth, npass)` is the callback; assign to `model.cuts_generator` (cutting planes, needs a complete initial formulation) or `model.lazy_constrs_generator` (true lazy constraints, only re-checked on integer-feasible incumbents, so the initial formulation can omit the connectivity constraints entirely — matches this project's separator-cut pattern well). Warm start: `model.start = [(var, value), ...]`, with the solver filling in unset auxiliary variables.
- Wheels/arm64: as of **python-mip 1.17**, CBC ships as a decoupled companion wheel, `cbcbox`, with **native arm64 macOS builds** (no more Rosetta fallback); python-mip 1.17.x supports CPython 3.10–3.13 and PyPy 3.11 — directly compatible with the project's Python 3.13 venv. Source: search results citing https://github.com/coin-or/python-mip/releases, https://pypi.org/project/cbcbox/, https://github.com/coin-or/python-mip/issues/406 (historical arm64 pain point, now resolved per the 1.17 release notes surfaced in search).
- License: EPL-2.0, confirmed via https://github.com/coin-or/python-mip/blob/master/LICENSE (matched in search).
- No native nonlinear/log handling — CBC/python-mip is LP/MILP only, so it would only ever serve as the **master-problem MILP solver** inside an outer-approximation loop (like the current HiGHS-based one), not as a standalone convex-MINLP solver.
- Parallelism: `-threads=N` in CBC's `CbcBaseModel` (compile-time-gated by `CBC_THREAD`); community consensus (pulp-or-discuss, or-tools issue #180 threads) is that CBC's parallel scaling is weak relative to commercial solvers, but present.

### OR-Tools CP-SAT
- Solution callback is read-only: `CpSolverSolutionCallback` fetched/confirmed via https://developers.google.com/optimization/reference/python/sat/python/cp_model and https://d-krupke.github.io/cpsat-primer/parameters.html (matched in search) — used for early stopping / logging intermediate solutions, **cannot inject constraints**. Explicit statement surfaced in search: "CP-SAT does not support adding lazy constraints from these callbacks (or at all)."
- `AddHint(var, value)` for warm start, confirmed via GitHub discussion google/or-tools#3277 (matched in search).
- Not a fit for the project's convex MINLP objective at all: CP-SAT's variables and expressions are integer/Boolean with a limited nonlinear vocabulary (`AddMultiplicationEquality`, etc., integer-only) — there is no continuous `log` term, so the log-Nash-welfare objective cannot be expressed directly. It could theoretically serve only as a **pure-MILP master solver** analogous to CBC/HiGHS in an externally-run OA loop, and even there it brings no lazy-cut advantage over HiGHS.
- `num_search_workers` for parallel portfolio search, confirmed via https://d-krupke.github.io/cpsat-primer/parameters.html (matched in search); "enumerating all solutions in parallel is not supported" (from a search-matched or-tools-discuss thread).
- License: Apache 2.0. Wheels: arm64 macOS wheels present on PyPI (`ortools-9.5.2237-...-macosx_11_0_arm64.whl` observed; current versions track newer builds).

### Pyomo + MindtPy
- Docs fetched directly (stable): https://pyomo.readthedocs.io/en/stable/explanation/solvers/mindtpy.html. Verbatim: **"The single tree implementation currently only works with CPLEX and GUROBI, more exactly `cplex_persistent` and `gurobi_persistent`."** This closes the door on single-tree/LP-NLP-BB with any open-source MIP solver — confirms the constraint stated in the task and rules MindtPy single-tree out entirely for this project.
- Multi-tree OA mode's supported `mip_solver` list per the same fetch: `gurobi, cplex, cbc, glpk, gams, gurobi_persistent, cplex_persistent, appsi_cplex, appsi_gurobi, appsi_highs` — **CBC, GLPK, and HiGHS (via `appsi_highs`) are usable as the open-source MILP master solver** for OA/ECP/GOA/ROA strategies. SCIP is conspicuously absent from that list (no PySCIPOpt/Pyomo `appsi` persistent interface for it as of this doc).
- GOA (Global Outer-Approximation) targets **nonconvex** MINLP with an optimality guarantee — heavier than needed for this convex problem, and per the fetched doc "more computationally expensive than... OA and ECP."
- Net effect: Pyomo+MindtPy's *only* usable mode here is **multi-tree OA**, which is architecturally the same shape as what the project already does by hand (outer approximation with a fresh MILP solve per iteration) — it would swap the hand-rolled OA loop for Pyomo's, but does not solve the lazy-connectivity-cut problem, since the connectivity cuts still have to be added between MindtPy's OA iterations, not inside a single MILP solve.
- License: Pyomo itself is BSD-3.

### Bonmin / Couenne
- Bonmin is COIN-OR, EPL-licensed (OSI-certified), confirmed via https://github.com/coin-or/Bonmin and matched search text ("Bonmin is a COIN-OR project licensed under the EPL"). B-BB (NLP-based branch-and-bound, single tree, closest analog to a real single-tree convex-MINLP solve), B-OA (outer approximation), B-QG, B-Hyb are the four algorithm variants; all run inside the compiled binary — there is no Python callback surface, so it cannot host the project's custom connectivity-separator logic without going through Bonmin's own (C++) heuristic/cut-generator plugin API, which is a much heavier lift than PySCIPOpt's `Conshdlr` or python-mip's `ConstrsGenerator`.
- Install: `conda install -c conda-forge coin-or-bonmin` per https://anaconda.org/conda-forge/coin-or-bonmin (matched in search) — **conda only, not a pip/PyPI wheel**, which conflicts with the project's plain-venv workflow (`/Users/ntlee/projects/td/.venv`) unless a conda environment is introduced alongside it, or the binary is built via coinbrew (macOS build has extra manual setup steps per https://www.coin-or.org/Bonmin/Install.html, matched in search).
- Couenne: same install/no-callback story, but targets nonconvex MINLP (spatial B&B) — no benefit over Bonmin B-OA for a convex problem, so not worth prototyping here.

### SHOT
- GitHub: https://github.com/coin-or/SHOT (matched in search). Algorithm: dual strategy combining extended supporting-hyperplane (ESH) and extended cutting-plane (ECP) polyhedral outer-approximation, giving a global certificate for **convex** MINLP (its main design target; nonconvex support since v1.0 is heuristic-only, no guarantee). Requires a MILP solver — **Cbc is an explicitly supported open-source choice** (alongside Cplex/Gurobi) — plus an NLP solver, for which **only Ipopt is currently supported**.
- No Python callback API found; it's driven via GAMS/AMPL/OSiL interfaces, and no PyPI wheel was found in this session's search — would require a source build. This makes it a heavier integration lift than PySCIPOpt or python-mip for a Python-native project, though its OA/ECP mechanics are exactly on point for the convex-MINLP structure described.
- License: COIN-OR project convention is EPL; the SHOT-specific LICENSE file (https://github.com/coin-or/SHOT/blob/master/LICENSE) was located but its exact text was not read in full this session — **flag as UNVERIFIED at the SHOT-specific granularity**, though very likely EPL given the ecosystem (Ipopt, Bonmin, Cbc are all EPL/EPL-2.0).

### Juniper.jl / Pavito.jl (Julia — note only)
- Juniper: LANL open-source nonlinear B&B in Julia, per https://arxiv.org/pdf/1804.07332 and https://lanl-ansi.github.io/Juniper.jl/stable/ (matched in search); parallelizes NLP subproblem solves across Julia workers; nonconvex support is heuristic (no global certificate), convex support is exact.
- Pavito: convex-MINLP outer approximation via MathOptInterface, analogous to Bonmin B-OA, per https://github.com/jump-dev/Pavito.jl (matched in search).
- Both are Julia-native; using either from this Python 3.13 project would require a Julia runtime plus a Python↔Julia bridge (PyJulia/juliacall) — extra infrastructure with no capability this stack lacks elsewhere (PySCIPOpt already gives a Python-native, single-tree-capable, globally-certified convex MINLP path). **Not recommended to prototype**, noted for completeness only per task instructions.

### GLPK (note only)
- `glp_intopt`'s native C API does expose branch-and-cut callback hooks (row generation, cut generation, branching, heuristics, "bingo") per GLPK's own docs (matched in search: https://lists.gnu.org/archive/html/help-glpk/2007-09/msg00069.html and glpk.h source). The only Python binding surfacing this is the third-party **pyglpk** (`Callback` class with `select/prepro/rowgen/heur/cutgen/branch/bingo` methods, per https://pyglpk.readthedocs.io/en/latest/object-documentation.html, matched in search) — this is **not** the GLPK path most Python users hit (that's typically `swiglpk` or GLPK via Pyomo/`mip_solver="glpk"`, neither of which exposes these callbacks). pyglpk's maintenance status and macOS arm64 wheel availability were **not confirmed** in this session — treat as UNVERIFIED and low priority; GLPK's B&B is also far weaker than CBC/SCIP/HiGHS on modern hardware, so it is not competitive regardless of callback access.

### Benchmarks
- **Mittelmann / plato.asu.edu**: Hans Mittelmann's "Latest Progress in Optimization Software" (INFORMS 2025, https://plato.asu.edu/talks/informs2025.pdf, and the benchmark index https://plato.asu.edu/bench.html, both matched in search) is the standard open MIP/MINLP benchmark. As of the 2024–2025 rounds, Gurobi and MindOpt withdrew from the public benchmark (Aug 2024 / Dec 2024 respectively per search-matched notes), so recent head-to-head numbers vs. Gurobi are thinner than historically; search-matched commentary states "HiGHS is about 20x slower than top commercial solvers on Mittelmann benchmarks" — direct HiGHS-vs-SCIP-vs-CBC numbers on ~1k-binary MIPs were not extracted line-by-line from the benchmark tables in this session (the PDF/table itself was not fetched, only search snippets) — **treat relative HiGHS/SCIP/CBC ordering as UNVERIFIED pending a direct read of the current MIP benchmark table** at https://plato.asu.edu/ftp/milp.html (or equivalent) before relying on it for a go/no-go decision.

## Ranked recommendation

**1. PySCIPOpt (SCIP) — primary candidate to prototype first.**
It is the only stack in this matrix that simultaneously offers (a) a genuine, documented single-tree lazy-constraint mechanism (`Conshdlr` + `consenfolp()` + `addCons()`) that maps directly onto "reject a candidate assignment mid-B&B if it disconnects, add the cut, keep going" without restarting the solve; (b) native nonlinear/convex-MINLP handling with a global certificate, which could let the log-Nash-welfare objective be modeled directly instead of via an external outer-approximation loop; (c) a zero-friction `pip install` on macOS arm64 with SCIP bundled since PySCIPOpt 5.0.0; and (d) a permissive Apache-2.0 license since SCIP 8.0.3. Concrete entry points: `pyscipopt.Model`, `Model.includeConshdlr()`, a `Conshdlr` subclass overriding `conscheck`/`consenfolp`/`conslock`, `Model.addCons()`/`addPyCons()`; warm start via `Model.createSol()`/`setSolVal()`/`trySol()`. Caveat: no in-process parallel B&B (single-threaded core solve) — verify wall-clock on the 400–800-binary target size before committing, and independently confirm the nonlinear-handler global-certificate claim against SCIP's own `cons_nonlinear` docs (flagged medium-confidence above).

**2. python-mip (CBC) — fastest to test as a drop-in for the existing connectivity-cut logic.**
`ConstrsGenerator` + `model.lazy_constrs_generator` is a close Python-idiomatic match for what the project's separator-cut loop needs today, and as of python-mip 1.17 / `cbcbox`, installation on this exact environment (Python 3.13, macOS arm64, plain venv, `pip install mip`) should be friction-free with native (non-Rosetta) CBC. It cannot host the log objective natively (LP/MILP only), so it would still sit inside an outer-approximation loop like today's HiGHS-based one — but unlike HiGHS, it would let the connectivity cuts be added as true lazy constraints inside a single MILP solve rather than a full restart, which directly targets the "each round a fresh `scipy.optimize.milp` solve" bottleneck named in the task. Concrete entry points: `mip.Model`, `mip.ConstrsGenerator`, `model.lazy_constrs_generator = MyGen()`, `model.start = [...]`.

**3. Pyomo + MindtPy (multi-tree OA, open-source mip_solver) — only if #1 and #2 both stall.**
Confirmed usable open-source `mip_solver` options are `cbc`, `glpk`, and `appsi_highs` — no SCIP, and single-tree mode is Gurobi/CPLEX-only (verbatim from Pyomo docs), so this option only reorganizes the existing hand-rolled OA loop into Pyomo's OA implementation without solving the lazy-cut restart problem; treat it as a fallback for standardizing the OA bookkeeping, not a fix for the core convergence issue. Concrete entry point: `pyomo.contrib.mindtpy`, `SolverFactory('mindtpy').solve(model, strategy='OA', mip_solver='appsi_highs', nlp_solver='ipopt', ...)`.

Not recommended to prototype: HiGHS-direct (no cut-injection API exists — confirmed absence, not a gap to work around), CP-SAT (no lazy constraints at all, and no native continuous/log support), Bonmin/Couenne/SHOT (no Python callback surface for the custom connectivity logic; conda-only or source-build installs), Juniper/Pavito (Julia, unnecessary given PySCIPOpt covers the same convex-MINLP-with-certificate ground in pure Python), GLPK (weak solver, only a niche unmaintained-looking binding exposes callbacks).
