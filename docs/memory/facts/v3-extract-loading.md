# Loading the real v3 extract (td#3, td#78)

Shapes, counts and aggregates only (`mem:workflow/confidential-data`). The decision these facts led to is `mem:decisions/loader-non-zip-ids`.

- **The real extract failed to load at `c5be768`** (m5 session 01a0ee3e fork 01a0efe6, 2026-09-29, shapes only). 5 cells had 5-character alphabetic ZIP ids, one cell each in fi, ifa, imo, national_chase and wells_fi. Together they held 0.08% of `m_rel`, had no rep books and only a vacancy-filler share. They look like the blank-ZIP placeholder that the pre-v3 exporter dropped. `load()` refused them before the CONUS rule, even though its docstring says blank ids drop there. td#78 fixed this.
- **What the loader does since td#78** (merged `42aef54`, 2026-09-30; checked against `td/data.py` there). `td.data.from_payload` accepts any string ZIP id. It refuses non-string ids and reports them only as a count ("ZIP ids not strings"). Ids that are not ZCTAs, including the blank-ZIP placeholder, drop in `data.conus` as "not a CONUS ZCTA", which counts them and never lists them. This holds until the loader's checks change.
- **The two Studios' extract copies differ** (2026-09-29, m5 session 01a0ee3e fork 01a0efe6; still true when checked with sha256 over ssh on 2026-09-30). Before #78 landed, the m5 hub copy had the 5 placeholder cells removed and the counts in `channels.json` recomputed, which leaves 28,977 cells and 10,981 ZIPs. The originals are in `~/td-extract-backup/` on m5, outside the repo. The m2 copy still has the 5 cells. Since #78, both copies should load. After the CONUS rule they should also agree, but no one has checked either copy on the real file; that is #3's check. A count that includes the dropped cells, such as the loaded cell count or `dropped`, differs between the Studios until the copies are made the same again.

## Running extracts through exporter v3 (td#3, td#61)

- **Exporter v3 needs a channel column to sum M per cell** (2026-09-29, m5 session 01a0ee3e fork 01a0efe6; `export/export_instance.py`, `CHANNEL_NAMES` at line 54 and the guard at line 202 on `db58fd3`). It looks for a column named `current_channel` or `channel`, in any case and with spaces read as underscores. If it finds none, it treats the file as one channel and stops with "M must be identical on every row of a cell" whenever M differs within a ZIP.
- **Exporter v3 accepts the pre-v3 combined-file extract** (same session, checked 2026-09-29 on a synthetic seven-channel extract, td main 3b430d4 against 4788759). The columns are the same, and the one file is passed to both `--sales` and `--opportunity`, with extra channel rows. The outputs differ from the old v3/v4 files in κ (now the median over all cells), the channel names, and the dropped `--graph`/`--states`. So `m_rel`, tau and k are not comparable with those files.
- **The first real v3 run** (m5, 2026-09-29, same session): 28,982 cells, 10,982 ZIPs, 168 reps, join 1.0, and ten channels: fi, priafs, ifa, wh, imo, wells_wh, national_chase, wells_fi, edj and career. ifa held 47.6% of opportunity. career had a single cell, carrying 5.2% of opportunity. 3,084 ZIPs had M imputed and 4,245 were headroom-repaired, which added 0.52% of M. These counts include the 5 placeholder cells above.
- **Checksums across Studios.** On 2026-09-29 the real v3 extract was on both Studios' td hub roots with identical checksums (`a15d5bf30dd7`, 227,623 bytes; same session). That was before m5 removed the placeholder cells (above). On 2026-10-01 the curator found the sha256 prefixes differ: m2 `b7092f503925`, m5 `39e2b475c3ab`.
